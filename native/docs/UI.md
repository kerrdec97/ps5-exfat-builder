## 3. How the schema drives the UI

* Settings page: sections = `SettingsSchema::sections()` in `sectionOrder()` (+ Tools when dependencies exist); cards per `group`; `advanced` rows behind "Show advanced"; `restartRequired` adds "Takes effect after a restart"; `enabledWhenKey` disables the row with a reason; `normalize()` errors show under the control and are not saved; "n settings differ" + Reset section; Reset all… confirms; Import legacy settings… calls `SettingsStore::importLegacy`. The Tools section lists every `DependencyRegistry` entry; other sections list the dependencies their settings name (`dependencyId`). Storage shows the temporary-files row.
* Job pages: `JobOptionsPanel` lists the `perJob` settings of the relevant sections (Build image: Build, Verification, Performance, Advanced, PS5 connection, plus PFS on the PFS tile; FPKG tile: FPKG, PlayGo, Firmware and SDK, Verification, Performance, Advanced; Packed folder: Build, Performance, Advanced; Image tools: Build (Convert and Edit only), Verification, Performance). The Backport page has no `JobOptionsPanel`: its options are the engine's own. A changed value shows "Overridden for this job" with "Default is X. Use default"; the panel returns the overrides map for `enqueue`.
* Queue detail panel: path-like parameters and the job's overrides ("Overridden" badge), attempt number, auto-retry countdown ("Retrying in 25 s · attempt 2 of 3").

## 4. Deviations from the proposal, with reasons

| Proposal | Implementation | Why |
|---|---|---|
| Focus ring painted by each widget 1 px outside its bounds | One transparent `FocusRingOverlay` over the window paints the ring around the focused widget | A Qt widget cannot paint outside its own geometry; the overlay keeps the exact spec (2 px, radius + 1, outside) for every control including QSS-styled ones. Inputs ring on any focus, other controls after keyboard focus (`WA_KeyboardFocusChange`). |
| Dialogs as frameless `QDialog`s | `Sheet`: a child widget of the main window with its own event loop | Captured in screenshots, never gets a native title bar, and the scrim covers exactly the window. |
| Sidebar `menu` icon, `logs` icon, `inbox` empty-state icon | `sidebar`, `file_text`, `queue` | Those names do not exist in the shipped icon set. |
| Settings sections fixed list of 13 | Only sections that have settings (or dependencies) are listed | Generated from the schema; absent modules add no empty sections. |
| `ui.lastPage`, `ui.sidebarCompact` in the settings store | QSettings (`window/geometry`, `window/sidebarCompact`, `window/lastPage`, `crash/lastAcknowledged`) | Window state is not a job setting; the schema is owned by modules. |
| Queue "finishes in about 24 min" | Shown as the running job's time left plus the queued count | Queued jobs have no estimate until they run. |
| Extract & verify and Edit as separate destinations | One Image tools page with four action tiles (Extract, Verify, Convert, Edit) | The actions share the opened image; each tile shows only its own options. |
| Mount config list keys as multi-line | Shown as one row per key; list values separated with `;` in the table | A table cell cannot edit line breaks; the page converts back to one repeated key per line before rendering. |
| Library/Backport table rows come from a scan job | Also true without the engines: hand-added or dropped folders are summarised in-app (`GameInfoReader`) | The library scan is merged into the list (`pages::mergeScanResult`): hand-added dumps stay, known games keep when they were first seen. The Backport list comes from the page's own scan, not from a job. |
| Per-page "Activity" wells on every job page | The job monitor (`ui/JobMonitor`): the form column of Build / Image tools / DLC gives way to it when the primary button starts a job, the Queue details column holds its compact variant, and the dock's running block keeps a 3-line tail plus a Watch button | One component shows stages with their times, the clocks, the live log console and the result everywhere; the dock hides its own running block for the job the page is watching. |
| Table header sort chevrons | Headers are not sortable yet | No table needed sorting for v1. |

## 6. Job states and the monitor

`fw::JobState` is the one lifecycle every view projects: Queued → Running ⇄ Paused → Cancelling → Cancelled, Running → Succeeded | Failed, and Interrupted for a job that was running when the app last closed (`jobs/Job.h` has the diagram). Only `JobQueue` moves a job between states; views use `JobRecord::isActive()` / `isWaitingToRetry()` instead of comparing states by hand. `JobQueue::startNow(id)` runs one queued job ahead of the others, also while the queue is paused (Build now, Retry); `Job::runsWhileHeld()` marks the system jobs (update check, problem report) that never wait for Resume. `JobQueue::heldChanged` tells the views when the queue is paused.

"Add to queue" puts a job on a list; the page's primary button starts its job at once (`startNow`). The queue runs whatever waits unless it is held, so `JobFormPage::submitClicked(false)` holds a queue that has nothing to do (none of the user's jobs running or waiting) before it adds the job: the job waits, more jobs join it, and "Start queue" (`holdQueue(false)`) runs them in order, after which the queue is not held and the next "Add to queue" begins a new list. A job added while others run or wait joins the line and the queue is not held by that. The hold is the same one the Pause control sets; what the views call it follows from the state (`ui::queueSwitch(held, running, waiting)` in `JobRows.h`): **Start queue** when it is held, jobs wait and nothing runs (a list being collected, a queue restored at start-up, a paused queue whose running job has ended), **Resume queue** when it is held while a job still runs, **Pause queue** otherwise. In the Start state the toast of "Add to queue" has a "Start queue" button, the Jobs dock shows a primary "Start queue (n)" button in its footer, the Queue page's header button reads "Start queue (n)", the header chip reads "Queue waiting · n", the status bar "n waiting · press Start queue", the Home tile "n waiting · press Start queue", and a waiting row "Waits for Start queue". `QueueCompletionWatcher` reports a finished queue only when nothing waits any more, so not while a list is collected and not when a job started by hand ends while the list still waits.

`ui::JobMonitor` (Wide on the form pages, Compact on Queue) follows a job id through `jobChanged` / `jobFinished` / `jobRemoved` and a 1 s tick for the clocks while it is visible. `ProgressSnapshot` now carries `elapsedMs`, `phaseElapsedMs` and `phaseMs` (time per stage; `ProgressReporter::finish()` freezes them when the job ends), which the stage timeline shows. `ui::LogConsole` is the live log: the job's records from `LogModel` as they arrive, following the newest line unless the user scrolled up. `JobFormPage::View` (Form | Monitor) is the page's own two-state machine; `setView()` is its only writer.

Other lifecycles that are explicit enums rather than flag clusters: `ConsoleSession::ConnectionState` (Offline / Connecting / Connected / Failed, one `stateChanged` signal that the hero card, the header chip and Home project), `BackportPage::RunState` (Idle / Preflight / Running / Cancelling; `setRunState()` is the only writer and refuses illegal steps, `enterRunning()` is the one gate into Running; scanning is a separate flag), `BuildImagePage::SpaceCheck` (the free-space check of the output folder; a start asks the drive again unless the last answer is positive and a few seconds old) and `MainWindow::UpdateState` (Idle / Checking / UpToDate / Available / Downloading / PendingInstall / Installing).
