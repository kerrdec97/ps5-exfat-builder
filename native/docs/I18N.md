# Interface languages

The interface is written in English and can be shown in other languages.
Everything is in `src/core/Tr.h` / `Tr.cpp` (`fw::i18n`), the catalogue files
in `src/app/resources/lang/`, and two tests: `tests/core/tst_i18n.cpp` (the
mechanism) and `tests/core/tst_i18n_source.cpp` (the source list and the
catalogues).

## How it works

* **English is the key.** `FW_TR("Add to queue")` looks the English text up in
  the loaded catalogue and returns the translation, or the English text when
  there is no entry. With no catalogue loaded (the default) it returns its
  argument at once, so with English nothing about the app changes.
* **One catalogue, loaded once.** `main()` calls `i18n::configure(":/lang",
  "<data>/lang")` and `i18n::load(code)` before anything is shown. The code is
  the environment variable `FW_LANG` if set, else the setting
  `general.language` (read straight from the settings file, because the
  settings store does not exist that early). The language changes with a
  restart. Worker threads may call `translate()` freely: a catalogue is
  complete before it is published and is never changed afterwards.
* **Catalogue files** are JSON:

  ```json
  { "code": "de", "name": "Deutsch", "englishName": "German",
    "strings": { "Add to queue": "Zur Warteschlange hinzufügen" } }
  ```

  Built-in ones are `src/app/resources/lang/<code>.json`, listed in
  `src/app/resources/lang.qrc` (the test fails for a file that is not listed).
  A file of the same name in `<data folder>/lang/` is merged over the built-in
  one entry by entry, or adds a language the app does not ship. Codes are
  `[a-z]{2,3}(-[A-Za-z]{2,4})?` (`de`, `pt-BR`, `zh-CN`); `en`, `qps` and
  `qps-rtl` are reserved; files whose name begins with `_` are not catalogues.
* **A translation cannot break the app.** A file over 8 MiB, not valid JSON,
  or whose `code` is not its file name is ignored. An entry is dropped (the
  English text is shown) when `i18n::entryProblem()` objects:
  * it is empty;
  * its placeholders (`%1`…`%99`, `%L1`, `%n`) are not the same set as the
    English text's (order and repetition are free);
  * the English text has no `<` and the translation has one, or the English
    text has tags and the translation's tags are not exactly the same ones
    (so a link target cannot be changed);
  * it does not have as many `&` as the English text (mnemonics, `&&`,
    entities);
  * it has control characters or direction overrides, or is far longer than
    the English text (more than ten times plus 200 characters).

  A `name` or `englishName` that is over 60 characters or holds `<`, `&`, a
  control character or a direction override is not used either; the other
  name, or the code, is shown in its place.

  What was ignored or dropped is written to the log (source `i18n`), each
  note once; `i18n::notes()` returns the notes.
* **The Language setting** (`general.language`, Settings › General ›
  Interface) is a choice list: "English" plus one entry per catalogue found by
  `i18n::available()` when the modules are registered, shown as
  "Deutsch (German)". `i18n::configure()` therefore runs before `AppContext`
  is created. A stored code whose catalogue has gone is reset to English when
  the settings are loaded. Tests that do not call `configure()` see English
  alone. The old app's `language` key is imported (`zh` → `zh-CN`, `pt` →
  `pt-BR`, a language without a catalogue → `en`).
* **Coverage.** `Language::coverage` is the share of the source list
  (`_source.json`, below) that has a usable entry.
* **Pseudo-language.** `FW_LANG=qps` loads no file and shows every translated
  text as `⟦text⟧`: whatever appears without the brackets is not marked (or is
  deliberately English). It is not in the picker. `--screenshot-pages` honours
  `FW_LANG`.

## Right-to-left languages

Arabic, Persian, Hebrew and Urdu are written right to left. `ar`, `fa`, `he`
and `ur` (also with a region, `ar-EG`) are known to be; a catalogue of any
other language says so with `"direction": "rtl"` (any other value, or none,
is left to right; the field cannot make a known RTL code LTR).
`Language::rightToLeft` and `i18n::isRightToLeft()` tell; `main()` then calls
`QGuiApplication::setLayoutDirection(Qt::RightToLeft)` before the first
window, and the whole interface is mirrored.

* **Mirrored by Qt:** layouts (rows, columns, grids, the shell: the sidebar is
  at the right), style-sheet widgets, item views (column order), scroll bars,
  line edits, combo boxes, check boxes, tab bars, menus.
* **Mirrored by the app** (custom painting and hand-placed geometry follow
  the widget's `isRightToLeft()`; helpers in `ui/Widgets.h`: `mirrored()`,
  `mirrorPainter()`): the sidebar items and their sliding bar (at the right
  edge), the Settings section list and its bar, Switch (on is the knob at the
  left, as in Windows), Segmented and its pill (first segment at the right,
  arrow keys as on screen), progress bars and the monitor's bar (fill from the
  right, band and sweep leftwards), the rate sparkline, badges (icon at the
  right), choice and format tiles, action cards, drop zone, disclosure and
  group chevrons (point left when closed), library tiles, list rows and
  covers, job rows, the hero and console banners, toasts (at the left edge,
  sliding in from it), the dropdown chevron and its room in the padding (the
  style sheet has no direction: FwStyle marks a right-to-left dropdown
  `fwRtl`), the custom layouts
  (`TwoColumnLayout`, `FlowLayout`, the home `TileGrid`). Icons that point the
  way one reads (back, forward, undo, the sidebar icon) are drawn mirrored
  (`isMirroredRightToLeft()` in `ui/Icons.h`); play, chevrons chosen by Qt and
  everything else are not.
* **Left to right in any language** (`keepLeftToRight()`, `leftToRightText()`,
  `keepColumnLeftToRight()`): paths, URLs, addresses, title IDs, hashes,
  versions, sizes and dates in tables, mono inputs (`textInput(…, true)`,
  `PathField`'s edit), `monoLabel()`, path labels, the log views (Logs page,
  live log, activity lines, kernel log), the hex preview, autoload and
  ShadowMount+ text boxes, the FTP breadcrumb and the FTP listing's size and
  date columns. A label marked so keeps its place in the row (right to left
  it starts at the right) and only its text is read left to right. A text
  box marked so still shows its placeholder ("New lines appear here…") right
  to left in a right-to-left language: Qt paints it in the application's
  direction, not the box's (a painter's direction is the application's
  unless it is set). Nothing is added to the text itself: no direction marks
  in stored values.
* **Text direction.** A label, button or painted name that has no
  right-to-left letters ("ShadowMount+", "PPSA01234", "+2") is read left to
  right in the place the layout gives it, as Qt does for a label. Arrows
  inside translated sentences ("→") are the translators' to turn. Numbers and
  units keep their Western digits.

**Testing.** `FW_LANG=qps-rtl` is the right-to-left pseudo-language: every
translated text as `⟧text⟦` (a right-to-left mark first, so that it is taken
for right-to-left text as a translation would be) and the window mirrored. It
is not in the picker. Render every page with it:

```
$env:FW_LANG = 'qps-rtl'
& "<build>\bin\exFAT Image Builder.exe" --screenshot-pages <folder>
```

(isolate the data folder as the screenshot scripts do). English words inside
the brackets show the usual effect of Latin text in a right-to-left paragraph
(a trailing full stop at the left); a real translation does not have it.
`tests/app/tst_rtl_layout.cpp` runs the window right to left; the existing
tests run left to right and must see nothing change.

## What is translated

Everything a person reads in the interface: page titles, buttons, labels,
captions, placeholders, tooltips, menus, toasts, sheets and dialogs, empty
states, table headers, status chips, the settings schema (section, group,
label, description, choice labels), job kind names, stage names, the summary
lines the app composes for the monitor and the queue.

English on purpose: log lines, the error texts of the engines (`fw::Error`),
problem reports, file names, setting keys, anything written to disk or to a
console, the release notes, accessibility object names that tests look up.

## Marking a string

Replace `QStringLiteral("…")` (or `QLatin1String`, `u"…"_s`, a plain `"…"`
given to a text sink) by `FW_TR("…")` when the text is read in the interface.
Keep the literal byte for byte: the English text is the key. The argument must
be string literals and nothing else (adjacent literals are joined); the
scanner refuses anything else.

**Mark** texts given to labels, buttons, check boxes, menus and actions,
tooltips, placeholders, window and sheet titles, table headers, combo items,
toasts, info bars, empty states, status texts; format strings whose result is
shown (`FW_TR("%1 of %2 files").arg(a).arg(b)`: wrap the format, not the
result); both arms of a plural choice; the fixed words a model's `data()`
returns for DisplayRole and ToolTipRole.

**Do not mark** object names, property names, setting keys, job kinds, JSON
keys, file names, paths, extensions, URLs, style sheets, bare HTML tags,
regular expressions, icon names, date and number formats, log categories, text
written to a log, a file or a console, accessible/object names that tests look
up, game data (titles, IDs), and text that is compared with other text for
logic. If a literal is both shown and compared, compare the English and show
the translation.

Rules that need a second look:

* **Sentences are whole.** Never build a sentence from marked fragments or
  from an optional "s": mark the whole sentence with placeholders and reword
  the code, not the English.
  `n == 1 ? FW_TR("%1 job done") : FW_TR("%1 jobs done")`.
* **Plurals** are two English literals chosen in code (`n == 1 ? … : …`);
  mark both. There is no plural engine.
* **Static tables** (`static const struct { …; QString label; }`) and
  file-scope `const QString x = QStringLiteral("…")` that is shown: use
  `FW_TR_NOOP("…")` in the table and `fw::i18n::translate(x)` where it is
  shown. A table is built once and may be built before the catalogue is
  loaded; `FW_TR` there would freeze the English text.
* **Identifier and label in one literal** (a tab id "Images" that is also the
  tab's text): the identifier stays English, the label is
  `i18n::translate(id)` at display, and the literal is marked `FW_TR_NOOP`.
* **File dialog filters**: mark the description and keep the pattern,
  `FW_TR("Archives") + QStringLiteral(" (*.zip *.7z *.rar)")`.
* **Data from other modules** (settings schema, job kinds, stage names, tool
  names, job state and verification names) is not marked where it is defined:
  the engines stay as they are, and the interface calls
  `i18n::translate(def.label)` where it shows the text. These texts reach the
  source list through the scanner (see below), not through `FW_TR`.
* **Numbers, sizes, durations** keep their format helpers; only unit words
  that are words ("files", "left") are translated, `GB`/`MiB`/`s` stay.
  The helpers (`core/FileUtil.h`) write the interface language's decimal and
  group separators in Latin digits ("441,1 GB", "18.442" in German); a
  language whose numbers are written in other digits (ar, fa, bn, …) keeps
  the English form.
* **One English text, one translation.** There is no context: "Build" is
  translated the same wherever it appears. If two uses need different words in
  some language, change the English of one of them.
* **When `FW_TR` runs.** The catalogue is loaded before `AppContext` exists,
  so `FW_TR` is right anywhere code runs after that. It is wrong in anything
  built once and kept: a static or file-scope object, a function-local
  `static const` table. Those take `FW_TR_NOOP` and are translated where they
  are shown.

After marking a file it must compile and the area's tests must pass unchanged.
The diff is marking only: no reformatting, renaming or rewording beyond what a
whole-sentence rule requires.

## The source list (`_source.json`)

`src/app/resources/lang/_source.json` lists every English text of the
interface, sorted, one per line: `{"text": …, "where": […]}`. `where` is a
hint for translators: the source file, `setting <key>`, `job <kind>`,
`<file> (stage)`, `<file> (tool)`. It is generated, never edited:

* `FW_TR` / `FW_TR_NOOP` literals anywhere under `src/`;
* the settings schema as the app registers it (sections, groups, labels,
  descriptions, choice labels and descriptions, file filters, unit words);
* job kind names (from the job registry), job state, verification and tool
  status names;
* outside `src/app`, by pattern (`tests/support/I18nScan.h`): stage names
  (`QStringLiteral` literals in the body of a `phases()` / `…Phases()`
  function, in the arguments of `setPhases()`, as the name given to `begin()`
  and `beginStep()`), and the name and purpose of a tool
  (`dependencies.add(id, name, purpose, probe)`).

A text that is only a number, or a number with its unit, is left out.

`tst_i18n_source` fails when the file differs from the code and prints what is
new and what is gone. To update, run that test once with `FW_I18N_UPDATE=1`:

```
$env:FW_I18N_UPDATE = '1'
ctest --test-dir <build> -R tst_i18n_source --output-on-failure
$env:FW_I18N_UPDATE = $null
```

and commit the file. On a merge conflict in `_source.json` take either side
and run the update again; never merge it by hand.

The same test checks every catalogue in the folder: valid JSON, `code` equal
to the file name, both names present, no entry whose key is not in the source
list (a stale key fails: remove it), every entry passes `entryProblem()`, no
leading or trailing space the English text lacks. A catalogue named in the
test's `shipped()` list must cover at least 98 % of the source list (the
missing keys are printed); others may be partial.

## Adding or correcting a language (users)

1. Open the data folder's `lang` folder (`%APPDATA%\kerrdec97\exFAT Image
   Builder Farewell\lang`, or `data\lang` next to a portable copy; create it
   if it is not there).
2. To correct a shipped language, create `<code>.json` (for German `de.json`)
   with only the entries to change:

   ```json
   { "code": "de", "strings": { "Add to queue": "In die Warteschlange" } }
   ```

   To add a language, give it a code, `name` (in the language itself) and
   `englishName`, and translate the texts of `_source.json`.
3. Keep `%1`, `%2`, `%n` and any `<b>`…`</b>` tags exactly as in the English
   text (their order may change), keep "…" as one character, keep file
   dialog patterns such as `(*.zip)`.
4. Restart the app and choose the language in Settings › General. An entry
   that cannot be used is shown in English and named in the log.

## Adding a language (developers)

Add `src/app/resources/lang/<code>.json`, list it in `lang.qrc`, and when it
is complete add its code to `shipped()` in `tests/core/tst_i18n_source.cpp`.
Glossary (never translated): exFAT, FFPKG, FFPFSC, PFS, UFS2, FPKG, PKG, AMPR,
PlayGo, ShadowMount+, fakelib, eboot.bin, param.json, Y2JB, FTP, SHA-256,
zstd, PS5, PS4, SDK, DLC, Backport (as the feature's name), product and file
names, key names (Ctrl, Enter, F5), anything inside `%1`. Tone: short, plain,
the polite imperative or infinitive the platform's own apps use (Windows 11 in
that language is the reference for Cancel, Settings, Browse, Queue…).
